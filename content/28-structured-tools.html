Programs need answers they can parse, and models need a way to ask for facts they cannot compute. Structured output forces replies into an exact JSON shape. Tool calling lets the model ask your code to run functions. Together they are the foundation of every automation and agent.

What you will learn

  • Explain how constrained decoding guarantees valid JSON
  • Get schema-checked output from LM Studio or Ollama with Pydantic
  • Explain the tool-calling loop and its wire format
  • Build a working two-tool assistant and handle bad calls safely

Constrained decoding

At every step the model scores every token (lesson 7.4). Constrained decoding adds a filter: a grammar describes every allowed output, and any token that would break it gets probability zero. Normal sampling then picks among the survivors.

Example: your schema says category must be "billing", "bug" or "other". After {"category": ", a token like "complaint" is impossible no matter how much the model wanted it.

Concept: valid is not the same as true

The grammar guarantees the shape, not the content. A field can be perfectly valid and completely wrong. Also, the schema constrains output but is not automatically explained to the model, so describe each field in your prompt too.

LM Studio and Ollama both run on llama.cpp, which converts a JSON Schema into its grammar format. Keep schemas simple: objects, arrays, strings, integers, booleans and enums. Some advanced JSON Schema features are not supported.

Structured output with Pydantic

Pydantic lets you define the schema as a Python class, send it, and validate the reply in one line.

from typing import Literal
from openai import OpenAI
from pydantic import BaseModel, Field

client = OpenAI(base_url="http://localhost:1234/v1", api_key="lm-studio")   # Ollama: port 11434
MODEL = "your-model-id"


class Ticket(BaseModel):
    category: Literal["billing", "bug", "other"] = Field(description="The kind of request")
    urgency: int = Field(ge=1, le=5, description="1 = can wait, 5 = urgent")
    summary: str = Field(description="One sentence, under 20 words")


email = "Hi, I was charged twice this month and need a refund before Friday."
r = client.chat.completions.create(
    model=MODEL, temperature=0,
    messages=[{"role": "system", "content": "Classify support emails. Fields: category, urgency 1-5, one-sentence summary."},
              {"role": "user", "content": email}],
    response_format={"type": "json_schema",
                     "json_schema": {"name": "ticket", "strict": True, "schema": Ticket.model_json_schema()}})
ticket = Ticket.model_validate_json(r.choices[0].message.content)
print(ticket)

Tool calling: the concept

A model can only produce text. It cannot check the time, do exact arithmetic or read a database. With tool calling you describe tools (name, purpose, argument schema). When the model wants one, it replies with a tool call instead of an answer. Your code runs the real function and sends the result back with role tool. The model then answers, or calls another tool.

Concept: the model never executes anything

Think of tool calls as requests. Your code decides whether to run them and with what arguments. That is why validating arguments in your tool code is not optional, especially with an uncensored model or untrusted input (lesson 6.4).

The wire format

  1. Your request includes a tools list.
  2. The model replies with tool_calls: each has an id, a function name and arguments as a JSON string.
  3. You append that assistant message, then one {"role": "tool", "tool_call_id": ..., "content": result} message per call.
  4. You call the model again with the extended messages.

Behind the scenes, the chat template (lesson 7.3) renders the tool definitions and calls into special text the model was trained on. Models trained for tool use (most current instruct models) do this far more reliably than older ones. LM Studio marks such models with a tool-use badge.

A working two-tool assistant

"""tools_demo.py: a calculator and a clock, called by a local model."""
import ast, datetime, json, operator
from openai import OpenAI

client = OpenAI(base_url="http://localhost:1234/v1", api_key="lm-studio")
MODEL = "your-model-id"
OPS = {ast.Add: operator.add, ast.Sub: operator.sub, ast.Mult: operator.mul,
       ast.Div: operator.truediv, ast.Pow: operator.pow, ast.USub: operator.neg}


def calculator(expression: str) -> str:
    """Safely evaluate + - * / ** on numbers (no eval of arbitrary code)."""
    def ev(n):
        if isinstance(n, ast.Constant) and isinstance(n.value, (int, float)):
            return n.value
        if isinstance(n, ast.BinOp) and type(n.op) in OPS:
            return OPS[type(n.op)](ev(n.left), ev(n.right))
        if isinstance(n, ast.UnaryOp) and type(n.op) in OPS:
            return OPS[type(n.op)](ev(n.operand))
        raise ValueError("only numbers and + - * / ** are allowed")
    return str(ev(ast.parse(expression, mode="eval").body))


def current_time() -> str:
    return datetime.datetime.now().strftime("%Y-%m-%d %H:%M")


FUNCS = {"calculator": calculator, "current_time": current_time}
TOOLS = [
    {"type": "function", "function": {"name": "calculator",
     "description": "Evaluate an arithmetic expression exactly, e.g. '17.5 * 3 + 2'.",
     "parameters": {"type": "object", "properties": {"expression": {"type": "string"}}, "required": ["expression"]}}},
    {"type": "function", "function": {"name": "current_time",
     "description": "Get the current local date and time.",
     "parameters": {"type": "object", "properties": {}}}},
]


def ask(question: str) -> str:
    messages = [{"role": "system", "content": "Use the tools for arithmetic and the current time. Never guess them."},
                {"role": "user", "content": question}]
    for _ in range(5):                                          # hard limit on tool rounds
        msg = client.chat.completions.create(model=MODEL, messages=messages, tools=TOOLS,
                                             temperature=0).choices[0].message
        if not msg.tool_calls:
            return msg.content
        messages.append({"role": "assistant", "content": msg.content or "",
                         "tool_calls": [tc.model_dump() for tc in msg.tool_calls]})
        for tc in msg.tool_calls:
            try:
                fn = FUNCS.get(tc.function.name)
                if fn is None:
                    raise ValueError(f"unknown tool {tc.function.name}")
                result = fn(**json.loads(tc.function.arguments or "{}"))
            except Exception as e:                            # unknown tool, bad JSON, bad arguments
                result = f"error: {e}"
            print(f"  [tool] {tc.function.name}({tc.function.arguments}) -> {result}")
            messages.append({"role": "tool", "tool_call_id": tc.id, "content": str(result)})
    return "Stopped after 5 tool rounds."


print(ask("What time is it, and what is 1234.5 * 17 minus 99?"))

Handling bad calls

  • Malformed JSON or unknown tools: send the error back as the tool result. Models usually correct themselves.
  • Loops: always cap the number of rounds.
  • Dangerous tools: anything that deletes, sends, spends or runs commands should ask a human first. Never pass model output straight into a shell.

Schema enforcement is on. Can the model still return a wrong value in a valid field?

  2. Yes. The grammar guarantees shape, not truth.
  3. Only at high temperature

Validate facts separately from format.

Who executes a tool call?

  1. The model
  2. LM Studio automatically
  3. Your code, after checking the arguments

The model only requests. Your code decides and runs.

Why cap the number of tool rounds?

  1. To stop endless call loops
  2. Because the API requires it
  3. To save disk space
