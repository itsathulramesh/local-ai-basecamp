A model with fewer guardrails shifts the responsibility to you. This lesson covers the practical rules: legal, safety, security and file hygiene.

What you will learn

  • Understand where the responsibility sits
  • Apply security habits specific to these models
  • Download and vet files safely
  • Know when not to use one

Responsibility

Running a model locally is legal in essentially every country. What is regulated is what is done with the output. Fraud, harassment, defamation, child sexual abuse material, and help with serious violence are unlawful whether a person, a script or a model produced them. Laws differ by place, so check your own. This is general information, not legal advice. The cloud providers' policies do not apply on your PC, so the judgement is yours.

Hard limits

Do not use any model to create sexual content involving minors, to target or harass real people, to produce malware or fraud tools for use against others, or to help harm anyone. Beyond the legal risk, these are plainly wrong, and many hosting platforms will ban you.

Security habits

  • Keep the server local. Do not bind Ollama or LM Studio to your network or the internet. An unauthenticated model server is a free GPU for strangers.
  • Treat the model as untrusted. It can be steered by text it reads (prompt injection). If you connect it to tools or files, it may follow instructions hidden in a web page or document. Without refusal training there is even less of a brake.
  • Do not give it dangerous tools. If you build an agent, limit what it can run and ask for confirmation before it deletes, sends or spends anything.
  • Keep separate models for separate jobs. Use a normal aligned model for anything public-facing or shared with other people.

File hygiene

  • Prefer GGUF and safetensors, as in lesson 3.2. Avoid pickle formats.
  • Prefer well-known uploaders with many downloads and a documented base model.
  • Check the licence. Fine-tunes inherit the base model's terms, and some bases restrict certain uses.
  • Do not run extra "launcher" executables, scripts or cracks bundled with a model download.
  • Where the uploader provides checksums, compare them. Download only from the official repository link, not from links in comments or forums.
  • Test new models in LM Studio or Ollama, not in scripts with access to your files.

Good reasons not to use one

  • You need accuracy. Abliterated models can be less truthful (lesson 5.2).
  • You are building something other people use. Keep guardrails in public products.
  • A simple prompt fix would solve your problem.
Concept: control and responsibility come together

The point of local AI is control. The cost of control is that nobody else is checking. Good practice is to be your own safety layer: local-only server, limited tools, honest use.

Check yourself

What is the most important network rule for a local model server?

  1. Make it public so you can reach it anywhere
  2. Keep it bound to your own computer unless you add authentication
  3. Disable your firewall

Local servers usually have no login, so exposing them gives strangers free access.

Which file would you trust least from an unknown uploader?

  1. A .gguf with a documented base model
  2. A .safetensors from the original lab
  3. A .exe "launcher" bundled with a model

Weights are data. Executables have no place in a model download.
