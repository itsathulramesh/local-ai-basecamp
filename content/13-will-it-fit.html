This is the most useful skill in the course. In one minute, with simple arithmetic, you can say whether any model will run fully on your GPU, run with help from system RAM, or not run at all, roughly how fast, and what to change.

What you will learn

  • Add up the four things that use VRAM
  • Estimate the KV cache for a given context length
  • Estimate the GPU + RAM split and its speed when a model does not fit in VRAM
  • Decide what to adjust when a model does not fit
  • Use the calculator and then check it against reality

The four consumers of VRAM

  1. Weights: parameters × bits ÷ 8 (lesson 3.1).
  2. KV cache: grows with context length. About 2 × layers × KV heads × head size × bytes per token.
  3. Overhead: the CUDA context and temporary buffers, roughly 1 to 1.5 GB.
  4. Windows itself: your desktop and browser take around 0.5 to 1 GB if this GPU also drives your monitor.
Concept: the context bill

For a typical 8B-class model the cache costs about 0.14 MB per token with the default 16-bit cache. At 32,000 tokens that is roughly 4.7 GB. That is nearly as big as the 4-bit weights. Halving the cache precision to 8-bit halves that cost.

The calculator

The calculator uses typical layer and head counts for each size class. Real models differ, and some use tricks such as sliding-window or hybrid layers that shrink the cache a lot. Use it for a first estimate, then confirm with nvidia-smi.

What to adjust when it does not fit

Work down this list in order:

  1. Lower the context length. The cheapest fix. Most chats do not need more than 8K.
  2. Quantize the KV cache to 8-bit. About half the cache memory, with small quality cost. In LM Studio this is the K and V cache quantization setting (marked experimental, and it needs Flash Attention on).
  3. Choose a lower weight quantization, for example Q5 to Q4.
  4. Choose a smaller model.
  5. Offload layers to system RAM. It works, more slowly. On small cards this is normal, and it is how a 4 GB GPU runs 7B to 12B models.

What spilling to RAM costs

Models are made of layers. If only some layers fit in VRAM, the rest run on the CPU using system RAM. For each token the GPU reads its share of the weights at GPU speed and the CPU reads the rest at RAM speed, so the time per token is roughly the sum of the two. System RAM is much slower to read than VRAM (dual-channel DDR4 is around 40 GB/s, versus 128 GB/s even on a GTX 1650 and 500+ GB/s on mid-range cards), so the RAM part dominates.

Example: a 12B model at Q4 (about 7 GB) on a 4 GB card with 16 GB RAM. About 2 GB of weights fit on the GPU and about 5 GB run from RAM, giving roughly 3 to 5 tokens per second. That is slower than reading speed but perfectly usable, and many people run models this way. The calculator above shows this split and estimates the speed.

The real limit is free system RAM. Windows and your apps need about 5 GB, so with 16 GB RAM roughly 11 GB is left for the part of the model that does not fit on the GPU. Past that, Windows swaps to disk and the model crawls.

Check yourself

A model fits at 8K context but not at 32K. What is the cheapest first fix?

  1. Buy more RAM
  2. Lower the context length
  3. Reinstall the driver

The cache grows with context, so shortening it frees VRAM immediately.

What happens if a few layers do not fit in VRAM?

  1. Nothing, speed is unchanged
  2. The model becomes more accurate
  3. Those layers run on the CPU and the whole model slows down

Spilled layers use system RAM and the CPU, which are much slower.

Which of these is NOT a normal consumer of VRAM while chatting?

  1. Your chat history saved on disk
  2. The model weights
  3. The KV cache

Saved history on disk uses disk, not VRAM. Only the text in the active context becomes cache.
