With so many models, what you need is not a ranking but a method. This lesson gives you a repeatable way to choose and a quick way to test.

What you will learn

  • Know the main kinds of model: base, instruct, thinking, coder, vision, embedding
  • Apply a three-step method for picking a model
  • Run your own small "shootout" to compare candidates
  • Read benchmarks with the right amount of scepticism

Kinds of model

KindWhat it isUse it for
BaseContinues text, does not follow instructionsFine-tuning starting point
Instruct / chatFollows instructions and chatsNearly everything
Thinking / reasoningWrites a chain of thought before answeringMaths, logic, planning. Slower.
CoderTuned on codeProgramming help
Vision (VLM)Accepts images as well as textScreenshots, diagrams, documents
EmbeddingTurns text into vectors for search. Does not chat.Search and RAG (lesson 6.3)

A three-step method

  1. Fit. Use the lesson 3.3 calculator to list the size classes and quantizations that fit your VRAM with the context you need.
  2. Fit the job. Take a model of the right kind for the task. Search for recent models in that size class with strong community feedback.
  3. Test on your own tasks. Public benchmarks do not know your work.

The mini shootout

Pick two or three candidates. Prepare ten real prompts from your work. Run each prompt on each model with the same settings, and score the answers 1 to 5 in a simple table. Also note tokens per second and VRAM used.

prompt | model A | model B | model C | notes
-------+---------+---------+---------+------
 1     |   4     |   3     |   5     | C wrote cleaner code
 2     |   2     |   4     |   4     | A hallucinated an API
 ...

It takes an hour and teaches you more than any leaderboard.

Reading benchmarks

  • Benchmarks measure narrow things. A high score on a maths test does not mean a model writes good emails.
  • Some models are tuned to the tests. Treat leaderboards as a way to find candidates, not to pick a winner.
  • Quantized, abliterated or merged versions score differently from the original. Test the exact file you will use.
  • Check the date. Rankings from six months ago are out of date.

Rules of thumb that last

  • The newest model in a size class usually beats older ones.
  • Bigger parameter count beats smaller at the same quantization, up to what you can run fast enough.
  • Mixture-of-experts models give the best quality per second when you have the memory.
  • For coding, choose a model that was trained for code or is known to be strong at it.
  • For long documents, check that its real context length is useful, not only advertised.

Check yourself

Why run your own ten-prompt comparison?

  1. Because it is required by Hugging Face
  2. Public benchmarks do not measure your tasks
  3. It makes the models faster

Only your own prompts show which model works for your needs.
